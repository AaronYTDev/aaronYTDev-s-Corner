void: a wrapper for xbps and runit

Last edited November 6th, 2026

Written by aaronYTDev

I have been running Void on my main machine for a while now. The distro is fine. xbps is fast, the packages are current, and nothing breaks often enough to be annoying. What is not fine is my memory. Every time I wanted to restart a service I ended up back on the runit documentation page, and every time I wanted to know what owned a file I typed the wrong xbps-query flag first. That is not a Void problem. That is a me problem, and the fix was a cheat sheet with a command line attached.

void-cli is that cheat sheet. One bash file, no build step, no dependencies past what a Void install already has. It does the package work through xbps, the service work through runit, and then there are the small things: void logs for following a service log, void doctor for checking the usual fresh-install problems, void cheat for the full systemd translation table. 

void pkg install htop neovim git
void svc enable --now bluetoothd
void logs -f NetworkManager
void doctor
void cheat

Installing it is two lines. install.sh drops the script in ~/.local/bin/void and the completion in the usual bash-completion directory, or you can put it in /usr/local with PREFIX.

Install does not touch the index

This is the one design decision that surprises people, so here it is first. void pkg install does not sync the repository indexes. It reads whatever index is already on disk and installs from that. void pkg update is the separate command that refreshes the indexes, and void pkg upgrade calls it before doing anything else.

The reason is that mixing the two is how you get a surprise upgrade. When the index is a month old but the archive URLs have moved, xbps has to refresh before it can install, and at that point it is holding a transaction built from one version of the index and a repository describing another. Half the time it is fine. The other half you were only after htop and come back to find that a library got bumped because something in the new index depended on a newer one. Keeping the two operations separate means an install is boring.

Starting a service enables it

runit does not have transient services. Nothing exists between "enabled" and "not enabled" the way systemd's systemctl start does, because a runit service is just a directory in /var/service and the supervisor reads it. So void svc start foo enables foo and then starts it. If that is not what you wanted, use void svc status first and read the state.

The rest of it is what you would expect once you stop looking for daemon-reload. There is no reload step: runit reads the run script at start, so editing is followed by void svc restart and nothing else. void svc create writes a run script plus a log/run with svlogd, so a new service starts out logging to /var/log/<name> instead of dropping output on the floor.

Parallel downloads, and why they barely help

xbps fetches archives one at a time. There is no switch for it, so void pkg install works around it: resolve the whole transaction first with xbps-install -n, pull the missing archives with curl several at a time, drop them in /var/cache/xbps, then run the real xbps-install and let it find everything already cached.

Every prefetched archive has to match the size the transaction advertised and then survive a zstd -t decompress test before it goes in the cache. That check is not paranoia. A corrupt archive sitting in the cache does not make xbps re-download it. It makes the whole transaction abort with an RSA signature error, and you get to run the command again. Fifty-seven milliseconds per archive is cheap compared to that.

The numbers on my machine, cold cache, 13 archives for neovim at about 23 MB: 6.6 seconds downloading serially, 4.1 with eight at a time. Which sounds good until you time the whole install and find it barely moves, 5.1 seconds either way, because unpacking and configuring dominate once the mirror is fast. The savings are real but they are in one phase, and that phase stops being the bottleneck quickly. On a slow or distant mirror it matters a lot more.

All of it fails soft. No curl, no xargs, no zstd, a dead mirror, a cache directory that is not writable, a package that vanished from the index: every one of those quietly falls back to a plain xbps-install with no complaint about parallelism.

Third-party repositories, and the ones that fight

void pkg repo manages /etc/xbps.d. There is a built-in catalog of 23 third-party repositories, and I checked each one by fetching <url>/<arch>-repodata and confirming an xbps index came back, so void pkg repo add blackhole does not hand you a URL that stopped publishing in 2024. {{arch}} expands to whatever xbps-uhelper arch says, so musl and aarch64 machines get the right path.

The interesting part is what happens when two of them publish the same packages. xbps resolves a package name from whichever repository it reads first and says nothing about the rest. The second repository is not an error, it is just invisible: its builds never get installed and its updates never show up. You find out months later when the package you have been waiting on is still on an old version.

So the catalog carries a conflicts field, and void pkg repo add refuses instead of quietly giving you a dead source. There are two groups worth knowing. BlackHole and its Russian mirror are the same 121 packages. BlackHole and sofijacom/hyprland-void overlap on 30 of the Hyprland repo's 33 packages, including hyprland itself, aquamarine, hyprlang and xdg-desktop-portal-hyprland. BlackHole is the wider source, with 91 packages the Hyprland repo does not have at all, so it is the one I keep. The Hyprland entry is there for the days when you want the compositor a version or two ahead of everything else.

What it does not do

It does not parallelise unpacking, which is the actual bottleneck, and I am not going to pretend otherwise in the readme. It does not track held packages back across an upgrade beyond what xbps-install already does. It has never been run on musl, though nothing in it is glibc-specific. The repo catalog is hand-checked rather than generated, which means it is accurate today and will need a look in a year.

What it is good at is the boring part. I stopped looking up runit commands. That was the whole goal.
